# core-api · C1–C9

Из корня репозитория запусти `make up`. Для запуска только базы и API подойдёт
`docker compose up -d --build --wait postgres && docker compose up -d --no-deps --build --wait core-api`.
При старте core-api применяет встроенные миграции к схеме `core`, затем загружает демоданные.
Загрузка повторяема и сохраняет изменения, внесённые в существующие записи.

## Проверка API

По умолчанию API доступен на `http://localhost:8080`. Тестовые аккаунты перечислены в
[data/README.md](../data/README.md). Для входа Анны:

```bash
curl -fsS http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"intern_anna","password":"buddy2026"}'
```

Скопируй поле `token` в переменную `TOKEN`.

```bash
curl -fsS http://localhost:8080/api/me -H "Authorization: Bearer $TOKEN"
curl -fsS http://localhost:8080/api/onboarding -H "Authorization: Bearer $TOKEN"
curl -fsS -X PATCH http://localhost:8080/api/onboarding/tasks/t_join_channels \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"status":"done"}'
curl -fsS 'http://localhost:8080/api/chat/messages?limit=2' -H "Authorization: Bearer $TOKEN"
curl -fsS http://localhost:8080/api/actions -H "Authorization: Bearer $TOKEN"
```

Вход выдаёт JWT HS256 на 24 часа. Используется общий `JWT_SECRET` из Docker Compose.
История и карточки доступны их владельцу. Статус задачи меняется только в плане
текущего пользователя.

Прогресс округляется до целого процента по доле выполненных задач. Следующие шаги
выбираются среди незавершённых задач по ближайшему сроку. При равном сроке приоритет
у задачи в работе, далее действует порядок чек-листа. Задачи без срока идут после
задач со сроком, заблокированные идут после доступных. Сроки считаются в календарных
днях от даты начала стажировки. Текущая дата берётся в часовом поясе Europe/Moscow.

## Чат и заявки

`POST /api/chat/messages` сохраняет сообщение, передаёт агенту проверенный профиль,
состояние адаптации, до 20 предыдущих сообщений и состояние диалога.
Текущим считается первый незавершённый этап. Агент также получает незавершённые
просроченные задачи. Если агент недоступен, API отвечает `200`, сохраняет
сообщение помощника со статусом `error` и сохраняет состояние диалога для следующего сообщения.
Пока один ход обрабатывается, второй параллельный ход того же пользователя получает `429`.

Ответ агента и карточки предложенных черновиков сохраняются одной транзакцией.
Предложенные агентом статусы применяются к задачам текущего пользователя. Выполненную
задачу агент не переоткрывает. Закрытие задачи, требующей выдачи доступа,
требует подтверждения выдачи корпоративным сервисом.

После `make up` агент вызывает MCP [corp-mock](../corp-mock/README.md), а
core-api отправляет и отменяет заявки по REST.

```bash
curl -fsS http://localhost:8080/api/chat/messages \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"text":"Хочу взять отгул завтра"}'

# Возьми id из assistant_message.actions в ответе и запиши его в ACTION_ID.
curl -fsS -X POST "http://localhost:8080/api/actions/$ACTION_ID/confirm" \
  -H "Authorization: Bearer $TOKEN" -H 'Idempotency-Key: confirm-demo-0001'
curl -fsS -X POST "http://localhost:8080/api/actions/$ACTION_ID/cancel" \
  -H "Authorization: Bearer $TOKEN"
```

Для подтверждения требуется `Idempotency-Key` длиной 8–128 символов. При
повторе подтверждения используй тот же ключ. Первый успешный ответ сохраняется
для пары «карточка и ключ» и возвращается при повторном запросе.
Перед обращением к операции отправки core-api читает статус заявки в corp-mock.
Если ответ потерялся, core-api проверяет статус ещё раз. Если результат остаётся
неизвестен, API возвращает `503`. После восстановления связи повтор использует
тот же ключ отправки для той же заявки.

## Синхронизация и уведомления

При чтении карточек, истории, адаптации и уведомлений core-api обновляет открытые
заявки через REST `corp-mock`, используя JWT владельца. При сбое возвращаются
последние сохранённые данные. Смена статуса карточки и связанной задачи записывается
в одной транзакции с уведомлением. Статус карточки в истории чата тоже обновляется.
Ответ повторного подтверждения с тем же ключом остаётся снимком первой операции.

Заявка на пространство команды относится к задаче `t_team_space`, заявки на
остальные рабочие инструменты — к `t_request_accesses`. Если задача уже явно
связана с карточкой, эта связь используется первой. Отправка переводит связанную
задачу в `in_progress`. Для завершения задачи требуется `fulfilled_at` у последней
связанной заявки на каждую из её систем. Если среди этих заявок есть ожидающая
выдачи, задача остаётся в работе. Отклонение или отмена блокирует незавершённую
задачу, когда ожидающих заявок больше нет.

Планировщик запускается при старте core-api и затем раз в минуту. Он создаёт
по одному напоминанию на каждый пропущенный срок незавершённой задачи.
Просрочка считается по календарной дате в Europe/Moscow.

```bash
curl -fsS http://localhost:8080/api/notifications -H "Authorization: Bearer $TOKEN"
```

## Диагностика

В каждом ответе core-api есть `X-Request-Id`. Этот же идентификатор передаётся
агенту и corp-mock. В JSON-логах по `request_id` можно найти HTTP-маршрут, результат,
длительность внешних вызовов и изменения статусов карточек и задач. Для планировщика
фиксируются результат запуска, длительность и количество новых напоминаний.

```bash
docker compose logs core-api | rg 'rq_ИЗ_ЗАГОЛОВКА'
```

## Тесты

`make test-core-api` проверяет форматирование, запускает статический анализ и тесты Go
в тестовом образе. Для проверки миграций, прав, восстановления заявок,
синхронизации, напоминаний и логов на PostgreSQL задай URL **пустой тестовой базы**:

```bash
cd core-api
CORE_TEST_DATABASE_URL='postgres://buddy:buddy@localhost:15432/buddy_core_test?sslmode=disable' \
  go test ./... -count=1
```
