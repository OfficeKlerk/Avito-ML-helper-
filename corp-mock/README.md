# corp-mock · T1–T8

Прямые REST и MCP вызовы ниже используют локальное дополнение Compose. [Включить локальные порты](../README.md#единый-вход-и-локальная-отладка).

`make up` запускает сервис на порту 8070. При старте он создаёт таблицы в схеме
`corp` и загружает записи `preloaded` из `data/seed/requests.json`. Повторный
запуск сохраняет статусы и результаты отправки. Для локального запуска Go
нужны `DATABASE_URL`, общий с core-api `JWT_SECRET` и `SEED_DIR` с тестовыми данными.

## Заявки

`GET /api/v1/requests/{request_id}` возвращает заявку владельцу. Владелец может
отправить черновик через `POST …/submit` и отменить черновик или отправленную заявку
через `POST …/cancel`. Только назначенный руководитель из той же команды может
согласовать или отклонить отправленную заявку через `POST …/approve` или
`POST …/reject`. Самосогласование запрещено. Недопустимый переход возвращает
`409 conflict`, чужая операция — `403 forbidden`.

При отправке укажи `Idempotency-Key` длиной 8–128 символов. У повторов сохраняется
номер заявки. Согласование заявки на доступ сразу
выдаёт доступ, заполняет `fulfilled_at` и меняет состояние в `access_list_my`
на `granted`. Для ранее согласованной заявки с пустым `fulfilled_at` руководитель
может завершить выдачу тем же вызовом. У отгула и отпуска `fulfilled_at` остаётся пустым.

Получить JWT можно через `POST http://localhost:8080/api/auth/login`. Для тестовой
заявки на Jira используй `intern_anna`, для согласования — `lead_olga`.
Тестовый пароль указан в [data/README.md](../data/README.md).

```bash
curl -fsS http://localhost:8070/api/v1/requests/req_anna_jira_1 \
  -H "Authorization: Bearer $TOKEN"
```

## Справочник

MCP Streamable HTTP работает по адресу `http://localhost:8070/mcp`. Передавай
JWT в `Authorization: Bearer …` при каждом запросе.

| Инструмент | Аргументы | Результат |
|---|---|---|
| `directory_get_me` | `{}` | Профиль, команда, наставник и руководитель текущего пользователя |
| `directory_find_contact` | `{"topic":"accesses"}` | Контакты своей команды и общие контакты по теме |

Допустимые темы — `accesses`, `absence`, `onboarding`. Если доступных контактов
нет, возвращается пустой список.

## Отгулы и доступы

| Инструмент | Назначение |
|---|---|
| `absence_get_rules` | Тестовые правила и предупреждение об их статусе |
| `absence_list_my` | Заявки текущего пользователя на отгул и отпуск |
| `absence_create_draft` | Черновик по датам `date_from` и `date_to`, виду отсутствия и ключу повтора |
| `access_list_my` | Обязательные системы, имеющиеся доступы и статус заявок |
| `access_create_draft` | Черновик на разрешённую систему с причиной и ключом повтора |

Срок подачи и длительность берутся из `data/seed/absence_rules.json`. Дни
считаются по календарю Europe/Moscow, обе даты входят в период. MCP сохраняет
черновик. Отправка происходит через REST после подтверждения в core-api.
Ключ создания действует в рамках пользователя, команды и типа заявки.
Для одной системы повторный запрос переиспользует открытый черновик, а
выданный доступ или отправленная заявка блокируют создание второго.

Для проверки запусти `make up`, войди как `intern_anna` и отправь в чат
«Хочу взять отгул завтра» или «Запроси доступ к GitLab». В ответе появится
карточка. Пример подтверждения — в [core-api/README.md](../core-api/README.md).

## Управляемые сбои

Чтобы включить тестовый маршрут `POST /test/faults`, укажи отдельный
`CORP_FAULT_TOKEN` в `.env` и запусти `make up`. Для каждого сценария маршрут
принимает один сбой для указанной заявки и REST-операции. Установка нового
сценария заменяет предыдущий. Сбой применяется один раз к вызову с правами на
операцию. Настройка хранится в памяти и сбрасывается при перезапуске.

```bash
curl -fsS -X POST http://localhost:8070/test/faults \
  -H "X-Corp-Fault-Token: $CORP_FAULT_TOKEN" -H 'Content-Type: application/json' \
  -d '{"request_id":"req_demo","operation":"submit","mode":"drop_response"}'
```

В примере подставь значение `external_id` черновика и экспортируй локально
тот же токен, что указан в `.env`. Затем подтверди карточку через core-api.
При потере ответа core-api сверяет статус по REST и возвращает сохранённый
номер заявки. Повтор подтверждения с тем же ключом возвращает тот же результат.

| Режим | Что происходит |
|---|---|
| `unavailable` | corp-mock отвечает `503` до выполнения операции |
| `delay` | До операции проходит `delay_ms` от 1 до 5000 мс. При отмене запроса за это время операция пропускается |
| `drop_response` | После успешной записи изменения corp-mock закрывает соединение без ответа |

Операции задаются как `read`, `submit`, `cancel`, `approve` или `reject`.
Для `read` доступны задержка и `503`.

## Тесты

[T1–T3](../openspec/specs/corp-mock-foundation/spec.md), [T4–T6](../openspec/specs/corp-mock-requests/spec.md), [T7–T8](../openspec/specs/corp-mock-status-faults/spec.md).

`make test-corp-mock` запускает тесты модели, прав и MCP. Для тестов миграции,
сохранения заявки, параллельных черновиков, выдачи доступа и отправки укажи URL пустой базы PostgreSQL:

```bash
cd corp-mock
CORP_TEST_DATABASE_URL='postgres://buddy:buddy@localhost:15432/buddy_corp_test?sslmode=disable' \
  go test -race ./... -count=1 -coverpkg=./internal/...
```
