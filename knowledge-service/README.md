# knowledge-service: K1–K7

Рабочий сервис поиска по базе знаний с проверкой прав. При запуске читает Markdown
из `KB_DIR`, проверяет весь корпус и создаёт фрагменты с постоянными ID. Предоставляет
поиск BM25 и чтение документа по контракту E. Ответ пользователю формирует `agent`.

В текущей базе 14 синтетических документов и 44 фрагмента. Добавлены инструкции по
выдаче доступов, передаче задач перед отсутствием, блокерам адаптации и доступам
двух команд. Существующие документы и источники агента сохранены.

## HTTP API

| Метод и путь | Результат |
|---|---|
| `GET /health` | Проверка запущенного сервиса, без JWT |
| `POST /v1/search` | `{"query": "как оформить отгул", "top_k": 3}` → `{"results": [...]}` |
| `GET /v1/documents/{doc_id}` | Полный Markdown без YAML-шапки и метаданные документа |

Для `/v1/*` обязателен `Authorization: Bearer <JWT пользователя>` с подписью HS256.
`JWT_SECRET` должен совпадать с core-api и corp-mock. Агент пересылает токен как есть.
Права берутся только из подписанных `sub`, `login`, `role`, `team_id`, `exp`, а не из
JSON или ответа LLM. `public` тоже требует авторизации. Для HR допустим `team_id: null`.

`query`: непустая строка до 1000 символов, `top_k`: целое 1..10, по умолчанию 5.
Неизвестные поля, неверный JSON, Content-Type и значения дают 422. Тело ограничено
64 KiB. Авторизация выполняется до проверки тела. Пустой поиск — 200 и `results: []`.
Нет/неверный JWT — 401, чужой документ — 403 без метаданных, неизвестный ID — 404,
недоступная база — 503. Ошибки используют общий формат. Ответы `/v1/*` — `no-store`.

## Запуск и проверки

Из корня репозитория с Docker:

```sh
make test-knowledge-service
make contracts
make eval-knowledge
make test-knowledge-agent
docker compose up -d --build --wait knowledge-service agent
```

Последняя проверка запускает настоящие agent и knowledge-service через Gunicorn
по HTTP: реальный клиент поиска, подпись JWT, разделение команд, чтение документа,
ответ агента с источником. LLM и заглушка поиска не используются. Corporate-сервис
не требуется для успешного ответа по базе; отрицательный случай проверяется при
недоступном corporate-сервисе. Полный путь заявок требует ещё реализаций C/T.

Локально с Python 3.12, из каталога `knowledge-service`:

```sh
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt -r requirements-dev.txt
.venv/bin/python -m pytest
.venv/bin/python -m evals.run --check
JWT_SECRET=local-dev-secret-change-me-32-bytes-min KB_DIR=../data/kb \
  .venv/bin/python -m gunicorn --bind 127.0.0.1:8060 --workers 2 'app:create_app()'
```

Значение секрета выше предназначено для локальной разработки. Для сквозного теста
в это же виртуальное окружение установите `../agent/requirements.txt` и запустите
`python ../integration/knowledge_agent.py`. Скрипт сам поднимает и останавливает
оба процесса; тестовые JWT подписывает случайным временным секретом.

В Compose `KB_DIR=/data/kb` уже подключён только для чтения. Невалидный корпус или
отсутствующий секрет останавливает запуск. Изменения файлов применяются после
перезапуска. По умолчанию агент уже использует настоящий knowledge-service.
Если раньше в `.env` был задан `AGENT_KNOWLEDGE_URL` на stub, удалите этот override
или замените его на `http://knowledge-service:8060`. Для незавершённого corp-mock
по-прежнему можно использовать `AGENT_MCP_URL=http://stub-corp-mock:8070/mcp`.

## Поиск и ограничения доступа

Нормализация: NFKC, нижний регистр, ё/е, русские основы слов Snowball, служебные слова,
небольшой словарь терминов (например daily/стендап и ВПН/VPN). Морфологические
объекты изолированы по потокам. BM25: k1=1.5, b=0.75, положительный IDF; веса текста,
заголовка раздела, названия документа и тегов — 1/3/2/1. Оценка дополнительно учитывает
долю совпавших слов запроса в разделе и заголовке. При равенстве порядок по chunk_id.

Для ответа требуется совпадение не менее 60% значимых слов запроса. Это консервативный
лексический поиск: редкие синонимы и сложные перефразировки могут дать пустую выдачу.
Поиск не генерирует знания и не подставляет ответы из проверочного набора.

Правила visibility работают как OR: public, team:<team_id>, role:<role>. Менеджер и HR
не получают дополнительные права автоматически. Кандидаты, document frequency и
средняя длина считаются только по разрешённым фрагментам. Добавление чужого документа
не меняет ни выдачу, ни оценки. Кеш ограничен 64 индексами на процесс и ключом из
точного набора разрешённых документов текущего неизменяемого корпуса.

```python
from app.knowledge import KnowledgeBase

knowledge = KnowledgeBase.load("../data/kb")
view = knowledge.authorize(authorization_header, jwt_secret=configured_secret)
results = view.search("как оформить отгул", top_k=3)
document = view.document("kb_absence_rules").to_dict()
```

Для Flask используется `knowledge_for_request()`. `KnowledgeView` не переиспользуют
между запросами разных пользователей. Получаемые словари не изменяют исходный корпус.

## Качество и воспроизводимость

[Разметка](evals/cases.yaml): 60 вопросов, исходно 40 dev и 20 holdout. Метрики:
доля вопросов с правильным фрагментом в top-1/3/5, MRR, точность пустых ответов и утечки.
Сравниваются обычный BM25 по точным словам и рабочий улучшенный поиск.

[Первый holdout](evals/reports/first-holdout.md): Recall@3 92,9%, пустые ответы 100%,
утечек 0. После разбора промаха «Правила отгулов» исправлены общие слова запроса и
нормализация служебных слов. [Последний отчёт](evals/reports/latest.md) показывает
регрессию тех же вопросов, а не новую независимую оценку. Набор малый и синтетический;
эти показатели не означают такую же точность на произвольных реальных запросах.

`make eval-knowledge` сохраняет JSON/Markdown, отпечатки корпуса, разметки и кода,
и завершится с ошибкой, если Recall@3 <85%, пустые ответы <90% или есть утечка в
любой исходной выборке. Эти проверки входят и в тесты knowledge-service.

## Формат и постоянные идентификаторы

Формат YAML — в [data/README.md](../data/README.md). Все поля обязательны; опечатки,
повторные ключи/ID, неверные даты, пустые правила доступа, нечитаемые файлы и ссылки
на файлы отклоняются. Для текущего корпуса обязательна пометка тестовой инструкции.

Каждый `## Раздел {#anchor}` — один фрагмент `<doc_id>#<anchor>`. Правка текста,
названия или порядка не меняет ID, пока сохранён якорь. Для нового смысла нужен новый
якорь; длинные разделы автор разделяет явными якорями. Вложенные `###` и блоки кода
остаются внутри фрагмента. Текст перед первым разделом, кроме необязательного `#`,
отклоняется, чтобы не терять вступление. `start_line`/`end_line` — внутренний диапазон
строк в Document.text с заголовком; в контракт E они не добавляются.
