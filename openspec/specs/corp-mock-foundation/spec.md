# Модель заявок, права и справочник corp-mock

## Требование T1. Состояние заявки

Сервис хранит заявки в PostgreSQL в схеме `corp`. При старте загружаются записи
`preloaded` из `requests.json`. Повторный запуск сохраняет текущие статусы.
Поддерживаются следующие переходы.

| Текущее состояние | Операция | Новое состояние |
|---|---|---|
| `draft` | `submit` | `submitted` |
| `draft`, `submitted` | `cancel` | `cancelled` |
| `submitted` | `approve` | `approved` |
| `submitted` | `reject` | `rejected` |

### Сценарий. Два параллельных подтверждения

- WHEN владелец одновременно отправляет один черновик с одним ключом
- THEN обе операции возвращают один номер, а в базе остаётся одна заявка
- AND повтор с тем же ключом возвращает текущее состояние этой заявки

### Сценарий. Отмена согласованной заявки

- WHEN владелец пытается отменить заявку в статусе `approved`
- THEN возвращается `409 conflict` и заявка сохраняет статус

## Требование T2. Проверка доступа

REST и MCP проверяют JWT HS256, срок действия и соответствие профилю из
тестового справочника. Чтение, отправка и отмена доступны владельцу в его
команде. Согласование и отклонение доступны назначенному руководителю той же
команды при условии, что он сам не владеет заявкой.

### Сценарий. Чужая заявка и самосогласование

- WHEN сотрудник запрашивает чужую заявку или стажёр согласует собственную
- THEN возвращается `403 forbidden` без данных заявки
- AND запрос с недействительным JWT получает `401 unauthorized`

## Требование T3. Профиль и тематический контакт

Справочник читает `users.json`, `teams.json` и `contacts.json` из `SEED_DIR`.
Инструменты MCP `directory_get_me` и `directory_find_contact` используют
профиль из проверенного JWT.

### Сценарий. Одна тема для двух команд

- WHEN стажёры из Доставки и Авто запрашивают контакты по теме `accesses`
- THEN каждый получает контакты своей команды
- AND пользователь без команды получает только общие контакты или пустой список
