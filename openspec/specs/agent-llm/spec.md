# agent-llm: подключение LLM

Задача A6 из [плана ML-ядра](../../../docs/team/01_ML_CORE_BACKLOG.md). Контракт ответа — B; инструменты — те же, что в [agent-tools](../agent-tools/spec.md).

## Purpose

С настоящей моделью агент отвечает свободнее, но пользуется тем же механизмом инструментов и тем же форматом ответа. Режим без модели остаётся: он используется по умолчанию и как запасной при любом сбое модели.

## Requirements

### Requirement: Выбор режима

Режим задаёт `LLM_PROVIDER`: `mock` (по умолчанию) — правила без модели; `openai` — любой OpenAI-совместимый API Chat Completions с вызовом инструментов. Для `openai` нужны `LLM_BASE_URL`, `LLM_MODEL` и, если сервис требует, `LLM_API_KEY`.

#### Scenario: По умолчанию модель не нужна
- WHEN `LLM_PROVIDER` не задан или равен `mock`
- THEN агент отвечает по правилам и не обращается к модели

#### Scenario: Неполная настройка
- WHEN `LLM_PROVIDER=openai`, но не задан `LLM_BASE_URL` или `LLM_MODEL`, либо `LLM_PROVIDER` неизвестен
- THEN агент не запускается и пишет в лог, какой переменной не хватает

### Requirement: Модель пользуется теми же инструментами

Модели доступны `knowledge_search`, `directory_find_contact`, `absence_get_rules`, `absence_create_draft`. Описания и параметры инструментов corp-mock берутся из контракта C, поиска — из контракта E.

#### Scenario: Модель не задаёт ключ идемпотентности
- WHEN модель вызывает `absence_create_draft`
- THEN агент сам подставляет `idempotency_key` = `<request_id>:absence_create_draft`; модель этого параметра не видит

#### Scenario: Неверные аргументы
- WHEN аргументы модели не проходят схему контракта
- THEN инструмент не вызывается, модель получает ошибку `validation` и может исправить вызов

#### Scenario: Ответ собирается из результатов инструментов
- WHEN модель закончила ответ
- THEN `sources` — фрагменты, которые вернул поиск; `proposed_actions` — черновики, которые действительно созданы; текст — ответ модели

#### Scenario: Токен не попадает в промпт
- WHEN агент собирает сообщения для модели
- THEN в них есть контекст пользователя из тела запроса, но нет токена авторизации

### Requirement: Предел числа вызовов и общий таймаут

`LLM_MAX_TOOL_CALLS` (по умолчанию 5) ограничивает число вызовов инструментов, `LLM_TIMEOUT_SECONDS` (по умолчанию 25) — время на ответ модели.

#### Scenario: Предел вызовов исчерпан
- WHEN модель запросила больше вызовов, чем разрешено
- THEN лишние вызовы не выполняются, а модель получает последний запрос без инструментов и должна ответить текстом

#### Scenario: Время вышло
- WHEN общий таймаут истёк
- THEN агент переходит в режим без модели

### Requirement: Текст модели не утверждает того, чего не было

Карточки черновиков в ответе берутся только из созданных черновиков. Текст пишет модель, поэтому агент его проверяет.

#### Scenario: Модель пишет о черновике, которого нет
- WHEN в ответе нет ни одного созданного черновика, а текст модели утверждает, что черновик или заявка создан, подготовлен, отправлен, оформлен или согласован
- THEN агент заменяет текст честным: черновик не создан

#### Scenario: Модель описывает будущее
- WHEN текст говорит, что заявка «будет отправлена» или «не создана»
- THEN текст остаётся как есть

### Requirement: Диалог об отсутствии переживает сбой модели

#### Scenario: Модель уточняет дату
- WHEN пользователь просит отгул или отпуск без даты и модель не создала черновик
- THEN в ответе есть `state` = `{"intent": "absence_request", "kind": ...}` и `missing_fields`, как в режиме без модели

#### Scenario: Следующее сообщение — при упавшей модели
- WHEN в `state` идёт оформление отсутствия, пользователь пишет дату, а модель недоступна
- THEN запасной режим продолжает оформление и создаёт черновик

### Requirement: Запасной режим при сбое модели

#### Scenario: Модель недоступна
- WHEN модель не ответила, ответила ошибкой или пустым текстом
- THEN агент отвечает по правилам, `status: degraded`, в `trace` есть неудачный шаг `llm`

#### Scenario: Черновик уже создан, а модель упала
- WHEN модель успела создать черновик и после этого перестала отвечать
- THEN запасной режим получает уже созданный черновик из результатов этого запроса и не вызывает `absence_create_draft` второй раз
