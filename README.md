## Что уже умеет агент

`POST /v1/chat` (контракт B). По умолчанию агент отвечает без LLM:

- **«Что мне делать дальше?»** — следующие шаги адаптации с причинами.
- **Отгул или отпуск** — находит инструкцию в базе знаний (источники в ответе), понимает даты («завтра», «в пятницу», «13 ноября», «с 13 по 15 ноября»), уточняет недостающую дату и создаёт черновик заявки в corp-mock. Заявка уходит на согласование только после подтверждения пользователем — это делает core-api.
- **Доступы** — какие есть, какие ждут согласования, каких не хватает; черновик заявки на названную систему, по одному на систему. Если система не названа — уточняет. На доступ, который уже есть или запрошен, черновик не создаётся.
- **Вопросы по базе знаний** — отвечает текстом найденных фрагментов с источниками. Если ответа нет — просит уточнить вопрос и даёт контакт из справочника.
- Если сервис не ответил — `status: degraded` и честный текст: черновик не создан, если он не создан.

Запусти `make up`. Вход — `POST /api/auth/login` с тестовым логином (например,
`intern_anna` / `buddy2026`). Пример сквозного вызова и подтверждения — в
[core-api/README.md](core-api/README.md), инструменты и REST — в [corp-mock/README.md](corp-mock/README.md).

В Compose по умолчанию используются настоящие сервисы. Старые переопределения
`AGENT_KNOWLEDGE_URL`, `AGENT_MCP_URL` и `CORE_CORP_MOCK_URL` на заглушки
можно убрать из `.env` для сквозного сценария.


### Подключение LLM

**Сервис — Yandex AI Studio, модель — YandexGPT** (`yandexgpt/latest`) через OpenAI-совместимый API Chat Completions с вызовом инструментов. Модель пользуется теми же инструментами, что и режим без LLM, и отвечает в том же формате. Без ключа агент работает по правилам — это режим по умолчанию.

Как получить ключ:

1. В консоли Yandex Cloud выбери каталог и скопируй его ID.
2. Создай сервисный аккаунт с ролью `ai.languageModels.user`.
3. Создай у него API-ключ с областью действия `yc.ai.languageModels.execute` и скопируй секрет — он показывается один раз.
4. Заполни `.env`:

```
LLM_PROVIDER=openai
LLM_BASE_URL=https://llm.api.cloud.yandex.net/v1
LLM_MODEL=gpt://<ID каталога>/yandexgpt/latest
LLM_API_KEY=<секрет API-ключа>
```

Подойдёт и другой OpenAI-совместимый провайдер с поддержкой `tools` — меняются только эти четыре переменные.

| Переменная | Что задаёт |
|---|---|
| `LLM_PROVIDER` | `mock` — без модели (по умолчанию), `openai` — с моделью |
| `LLM_BASE_URL` | Адрес API до `/chat/completions`; для Яндекса `https://llm.api.cloud.yandex.net/v1` |
| `LLM_MODEL` | Имя модели у провайдера; для Яндекса `gpt://<ID каталога>/yandexgpt/latest` |
| `LLM_API_KEY` | Ключ, если провайдер его требует. Хранится только в `.env`, в репозиторий не попадает |
| `LLM_TIMEOUT_SECONDS` | Общее время на ответ модели, по умолчанию 25 |
| `LLM_MAX_TOOL_CALLS` | Предел вызовов инструментов за одно сообщение, по умолчанию 5 |

Задай их в `.env` и перезапусти: `make up`. Модели в контексте передаётся календарь на две недели: без него YandexGPT ошибалась с днём недели («в понедельник» → вторник). Если модель не отвечает, отвечает ошибкой или время вышло, агент отвечает по правилам со `status: degraded`. Черновик, который модель успела создать, второй раз не создаётся. Если `LLM_PROVIDER=openai`, а `LLM_BASE_URL` или `LLM_MODEL` не заданы, агент не запускается и пишет в лог, чего не хватает. Системный промпт — [agent/prompts/system.md](agent/prompts/system.md).

### Проверка качества

```bash
make eval
```

Одна команда прогоняет 23 проверочных случая (`agent/evals/cases.yaml`) без модели и, если LLM настроена в `.env`, с моделью. Мерится:
- выбор инструментов и действия;
- источники;
- отказы: документы другой команды и роли, чужие данные, самосогласование;
- инструкции внутри документов и сообщений;
- честность текста.

Отчёт сохраняется в [agent/evals/reports/latest.md](agent/evals/reports/latest.md). Последний прогон: **23/23** без модели и с YandexGPT, утечек 0, нечестного текста 0.

Эта проверка агента использует отдельную локальную среду из `data/` с документом-ловушкой (`agent/evals/environment.py`). Набор без модели прогоняется и в `make test-agent`. Известное ограничение: в источники попадает всё, что вернул поиск, даже фрагменты, которые модель не использовала.

Настоящий поиск отдельно проверяется на 60 размеченных вопросах: `make eval-knowledge`.
Сравнение с базовым BM25, метрики, первый отложенный прогон и последующая регрессия —
в [отчёте knowledge-service](knowledge-service/evals/reports/latest.md).
`make test-knowledge-agent` проверяет настоящий агент и поиск по HTTP, включая JWT,
источники и запрет чтения документов другой команды. Ключ LLM для этих проверок не нужен.

## Быстрый старт

Нужен Docker Engine 28+ или Docker Desktop с Linux-контейнерами, Compose v2.24.4+ и BuildKit. Для локального стенда закладывай 2 CPU, 4 ГБ памяти Docker и 10 ГБ свободного диска. `make` нужен для сокращённых команд и тестов.

```bash
docker compose up -d --build --wait
```

Открой http://localhost:3000 и войди как `intern_anna` с паролем `buddy2026`. `make up` делает тот же запуск. Без `.env` используются локальные настройки и агент в режиме `mock`. Для изменения настроек скопируй [.env.example](.env.example) в `.env`.

### Единый вход и локальная отладка

nginx отдаёт интерфейс и направляет `/api/…` в core-api с того же адреса. Прямые ссылки на страницы открывают SPA. Для отсутствующих файлов в `/assets/` возвращается 404. По умолчанию на хосте опубликован только интерфейс на `127.0.0.1:3000`. Проверка API через него, например, `GET /api/me` с JWT из входа.

Для прямых запросов к сервисам, PostgreSQL или разработки UI через Vite включи локальное дополнение:

```bash
docker compose -f docker-compose.yml -f docker-compose.debug.yml up -d --build --wait
```

Оно открывает на `127.0.0.1` порты core-api 8080, agent 8090, corp-mock 8070, knowledge-service 8060 и PostgreSQL 15432. Порты задаются в `.env`. `make smoke` запускает заглушки отдельно и проверяет контракты внутри сети Compose.

### Стенд с HTTPS

Привяжи DNS домена к хосту и открой входящие TCP 80 и 443. В отдельной конфигурации стенда задай `PUBLIC_DOMAIN`, свой `JWT_SECRET` длиной от 32 байт и `POSTGRES_PASSWORD`. Для пароля PostgreSQL используй символы, допустимые без кодирования в URL, например случайную hex-строку. Для демостенда с тестовыми аккаунтами и стандартными паролями ограничь вход сетью или IP участников.

```bash
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build --wait
```

Caddy получает и обновляет сертификат, перенаправляет HTTP на HTTPS и передаёт запросы nginx. Публикуются только порты Caddy. Сертификаты сохраняются в томе `tls-data`. Для управления этим стендом передавай оба файла Compose и те же настройки окружения.

### Данные, версии и тестовый сброс

Состояние хранится в томе `pgdata` проекта Compose. При первом старте PostgreSQL создаёт схемы `core` и `corp`, сервисы применяют миграции и загружают демоданные. Повторный запуск сохраняет существующие записи. `docker compose down` и `make down` сохраняют том. Для существующего тома PostgreSQL изменение пароля в `.env` требует отдельно сменить пароль роли в базе.

Базовые образы закреплены по digest. В проекте используются PostgreSQL 16, Go 1.23, Python 3.12, Node 22 и nginx 1.28. Версии Python-пакетов закреплены в `requirements*.txt`, Go-модулей — в `go.mod` и `go.sum`, npm — в `package-lock.json`. Файлы окружения исключены из Git и из сборки интерфейса.

Для отдельного тестового стенда доступны команды:

```bash
make test-stack-up
make reset-test-data CONFIRM=ai-buddy-local-test
```

Интерфейс тестового стенда — http://localhost:13000. Сброс останавливает контейнеры и удаляет том только у проекта `ai-buddy-local-test`. Это имя зарезервировано для тестового стенда. Следующий `make test-stack-up` создаёт чистую тестовую базу.

## Тесты

```bash
make test
```

Тесты одного сервиса: `make test-agent`, `make test-knowledge-service`, `make test-core-api`, `make test-corp-mock`, `make test-web-app`. Отчёт о покрытии печатается в конце каждого запуска. `make test` также запускает интеграцию агента с настоящим поиском.

`make test-core-api` и `make test-corp-mock` не поднимают базу, поэтому тесты с PostgreSQL в них пропускаются. Полный прогон с покрытием — `make test-core-api-db` и `make test-corp-mock-db`: пересоздают пустую тестовую базу в PostgreSQL из Compose и запускают тесты в контейнере Go. Здесь любой пропущенный тест — ошибка. Обе команды входят в `make test`. Последний прогон: покрытие внутренних пакетов core-api 85,1%, corp-mock 85,3%.

```bash
make integration
```

Общая сборка (I1): поднимает отдельный стенд с чистой базой, на своих портах и без LLM, проверяет, что ни один сервис не смотрит на заглушку, и проходит контракты A–E на настоящих сервисах. Путь такой: вход с настоящим JWT → вопрос с источником и открытие этого источника → повтор с `Idempotency-Key` → отгул через агента, MCP и corp-mock → подтверждение → уведомление → событие метрик. Отдельно проверяются прямые вызовы agent, corp-mock (REST и MCP) и knowledge-service. Каждый ответ сверяется со схемой контракта, у каждого вызова есть предел времени. После проверки стенд удаляется, его лог — в `reports/integration-compose.log`. Проверка контрактов по примерам без сервисов — `make contracts`, по заглушкам — `make smoke`.

`make lint` проверяет Python-код ruff; Go проверяется gofmt и vet, TypeScript — typecheck в тестах сервисов.

**CI** (`.github/workflows/ci.yml`) на каждый PR и push в main запускает `make contracts`, `make lint`, `make test` и `make integration`; логи с покрытием сохраняются как артефакты. Платная LLM в CI не нужна. Прогон `make eval` с моделью запускается только вручную (Actions → CI → Run workflow → llm) и требует секретов `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL`.

Все данные в проекте синтетические. Тестовые инструкции не являются регламентами Авито.
