# Диагностика и проверка развёртывания

## Диагностика

- Из корня репозитория выполни `docker compose ps -a` для проверки готовности контейнеров. Команда `make health` проверяет `/health` у core-api, agent, knowledge-service и corp-mock внутри Compose. PostgreSQL проверяется через `pg_isready`, web-app — запросом к `/`.
- При ошибке в браузере скопируй заголовок `X-Request-Id` ответа из вкладки Network. Найди его в `docker compose logs --since 10m web-app core-api agent knowledge-service corp-mock` через `grep -F '<идентификатор>'` или `Select-String -SimpleMatch '<идентификатор>'` в PowerShell. В логе доступа nginx записываются метод, HTTP-статус, время и идентификатор. Для ответов прокси используется идентификатор core-api, для ограничения частоты — идентификатор nginx. Агент не пишет в журнал содержимое полей невалидного запроса или текст неожиданного исключения.
- Подключение nginx к core-api ограничено 5 с, ожидание ответа — 90 с между чтениями. Таймаут вызова агента из core-api — 40 с. Агент ограничивает время обращения к модели 25 с по умолчанию и 20 с на HTTPS-стенде. Обычный таймаут поиска и MCP — 5 с, с учётом оставшегося времени. При сбое модели агент продолжает по правилам.
- На HTTPS-стенде Caddy допускает адреса из `PUBLIC_ALLOWED_CIDRS`. Он использует адрес соединения, поэтому при дополнительном балансировщике ограничь клиентов на его входе. Управляемые сбои corp-mock доступны при явном включении на локальном тестовом стенде. HTTPS-конфигурация отключает их.
- Лимиты HTTPS-стенда общие для экземпляра nginx. Для входа действует средний темп 20 запросов в минуту и допуск до 10 дополнительных запросов подряд. Для отправки в чат — 6 в минуту и допуск до 3 дополнительных запросов подряд. Допущенные запросы обрабатываются сразу. Превышение возвращает `429` с `Retry-After: 10`.
- HTTPS-стенд по умолчанию запускается с `PUBLIC_LLM_PROVIDER=mock`, без внешних запросов модели. Если нужна модель, установи `PUBLIC_LLM_PROVIDER=openai` и передай `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` агенту из локальной конфигурации. Агент допускает до трёх вызовов инструментов модели на сообщение и запрашивает до 500 выходных токенов на один ответ провайдера. Денежный лимит задаётся у провайдера. Ключ передаётся только контейнеру агента.

## Чистый запуск и откат

Нужны Docker и Compose по [README](../../README.md#быстрый-старт), Git и Node.js 22+. Из полного клона репозитория на проверяемом коммите запусти:

```bash
node integration/check-deployment.mjs
```

Скрипт использует чистые копии из Git и отдельный Compose-проект с синтетическими данными и портом `13056`. Для другого свободного порта задай `D6_WEB_PORT`. По умолчанию выполняется откат на `76f8a46`, использованный в [ручной приёмке](06_RELEASE_ACCEPTANCE.md#локальная-проверка-восстановления-d6--15-ноября-2026-года). Другой совместимый предыдущий коммит можно передать первым аргументом.

Проверка запускает сервисы с чистым томом, открывает SPA и статический файл через браузерный прокси, входит через API и отправляет заявку. Она сравнивает номер и статус заявки, историю и уведомление после остановки и повторного запуска, отката и возврата к новой версии. Между этапами `docker compose down` сохраняет том. После прогона удаляется только тестовый проект и его том. SHA развёрнутых коммитов, сведения об образах и результаты записываются в `reports/d6/*/deployment.log`. В Actions этот файл входит в артефакт `integration-reports`.
