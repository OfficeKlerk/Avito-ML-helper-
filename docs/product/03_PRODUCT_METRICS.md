# M1–M2. Метрики пользы и отчёт по событиям

Гипотеза пилота: с AI-buddy стажёр чаще доходит до результата без повторного обращения к наставнику и тратит меньше времени. Гипотеза проверяется отдельно для каждого [сценария релиза](01_RELEASE_JOURNEYS.md).

## Что считаем

Одно прохождение — один сценарий одного участника с новым `scenario_id`. В B3 оно начинается с первого `scenario_started`. Повторы одной отправки сохраняют идентификаторы. Завершение определяется следующим образом.

| Сценарий | Когда измерение заканчивается | Что проверяет наблюдатель |
|---|---|---|
| Адаптация | Сохранён ответ помощника со статусом `ok` или `degraded` | Участник верно назвал следующий шаг и причину, либо указал, что активных задач больше нет. |
| Вопрос по базе знаний | После сохранённого ответа открыт источник | Ответ относится к вопросу, а открытый раздел подтверждает его. |
| Отгул | Все подтверждённые в прохождении заявки согласованы | Участник видит номер и сохранённый результат. Отдельно фиксируется время до отправки, чтобы отличить работу стажёра от ожидания руководителя. |
| Доступ | По всем подтверждённым в прохождении заявкам сервер зафиксировал фактическую выдачу | Участник видит выдачу и обновление связанной задачи, когда выполнены её условия. |

| Метрика | Числитель, знаменатель и источник | Сравнение с базой |
|---|---|---|
| Время до результата | Для завершённых прохождений разность между временем конца из таблицы выше и началом. В отчёте медиана и число завершённых прохождений. В наблюдении время измеряется от выдачи задания до проверки результата. | Медиана по тому же сценарию при работе по инструкции, с тем же правилом остановки. |
| Доля завершений | Число завершённых прохождений / число начатых. Отчёт использует события B3, а наблюдатель отмечает фактический исход в обеих группах. | Та же доля при работе по инструкции. Незавершённые попытки остаются в знаменателе. |
| Повторные обращения к наставнику | Число прохождений с двумя и более отдельными обращениями / число начатых. B3 использует разные `event_id` для `human_help_requested`. Наблюдатель отмечает обращения и в базовом варианте. | Та же доля при работе по инструкции. Системные уточнения помощника не считаются обращениями к наставнику. |
| Полезность | После каждой попытки участник отвечает по шкале 1–5 на вопрос «Насколько выбранный способ помог выполнить задание?». Доля оценок 4–5 среди полученных ответов. Пропуски фиксируются отдельно. | Та же анкета после работы по инструкции. B3 этой оценки не содержит. |

## Как провести пилот

1. Подготовить две равноценные версии каждого задания на синтетических данных. Участник проходит одну с помощником, другую по инструкции. Чередовать порядок вариантов между участниками.
2. Выдавать задание в одинаковых условиях. До прогона согласовать предел времени и критерий результата. Для заявок держать одинаковый порядок и интервал действий тестового руководителя.
3. На каждую попытку записать обезличенный номер участника, вариант, сценарий, время начала и конца, исход, число обращений и ответ анкеты. Для технического прогона B3 отправить `scenario_started` до первого запроса, передавать одну пару заголовков сессии и сценария в ходе чата, отправлять `source_opened` после успешного открытия и `human_help_requested` при обращении. Формат описан в [core-api](../../core-api/README.md#события-для-метрик-пользы).
4. Сопоставить результаты по каждому сценарию и указать размеры выборок, пропуски и условия прогона. Вариант с реальной моделью и режим по правилам измерять на отдельных стендах или базах. Обычный интерфейс пока не передаёт метки B3. Для сравнения двух вариантов основным источником остаётся карточка наблюдения, а события дают техническую сверку.

## Как собрать отчёт M2

Запускай из корня проекта в Bash. В базе должны быть события одной выборки и одного режима. Для отчёта нужен Node.js 22+.

```bash
docker compose exec -T postgres sh -c 'psql -XqAt -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < scripts/metrics/export.sql > events.json
node scripts/metrics/report.mjs test rules < events.json
node --test scripts/metrics/report.test.mjs
```

В PowerShell:

```powershell
$events = Get-Content -Raw scripts/metrics/export.sql | docker compose exec -T postgres sh -c 'psql -XqAt -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
if ($LASTEXITCODE -ne 0) { throw 'Не удалось выгрузить события' }
$events | node scripts/metrics/report.mjs test rules
```

Если стенд запущен с именем проекта, укажи его в команде Compose.

Обязательные аргументы отчёта — выборка `test` или `pilot` и настроенный режим `rules` или `model`. В отчёте отдельно считается `degraded`: это число прохождений с упрощённым ответом, включая сбои инструментов. B3 не хранит причину такого ответа. Не объединяй в одной выгрузке разные выборки или режимы.

Выгрузка заменяет идентификаторы владельца, сессии, сценария и карточки порядковыми номерами прохождений и карточек. Она не включает переписку, имена, токены и пароли. В итоговом отчёте остаются только агрегаты. Дубликаты событий удаляются, счётчики воронки учитывают каждое прохождение один раз. Записи без начала считаются в `withoutStart`, а доля и медиана при отсутствии знаменателя или результата возвращаются как `null`. Ошибки ответа и отказ или отмена заявки считаются отдельно от незавершённых прохождений.
