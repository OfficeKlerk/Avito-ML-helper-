# AI-buddy (Авито, Hack&Change 2026) — разбор ТЗ и распределение ролей

## 1. Суть задачи в двух фразах
Сделать **прототип ИИ-помощника для стажёра**, который помогает освоиться в команде: отвечает на рабочие вопросы с учётом контекста, показывает этапы адаптации, статусы и следующие шаги, и **выполняет хотя бы одно действие через корпоративный сервис (или его имитацию)**. Цель бизнеса — снять с наставника рутину (сейчас 40–48 ч за 6-месячную программу и 55–65 ч за 9-месячную), не заменяя живое общение.

## 2. Что именно требуется (п. «Постановка задачи», 6 пунктов)
| # | Требование | Как закрываем |
|---|---|---|
| 01 | Описать путь стажёра в первые недели, выбрать сценарии по чек-листу Авито | CJM + сценарии S1–S4 (+S5) — роль 1 |
| 02 | Отвечать на вопросы о команде и инструментах с учётом контекста | RAG с фильтром по правам и контекстом (команда/роль/неделя) — роль 4 |
| 03 | Реализовать все сценарии, в одном — действие через корп. сервис/имитацию | Отгул и доступы через corp-mock (MCP), подтверждение в UI — роли 3, 4, 5 |
| 04 | Показать этапы адаптации, статусы задач, следующие шаги | Панель адаптации + next_steps + ИИ-крон напоминаний — роли 2, 3 |
| 05 | Обосновать архитектуру, права, подключение корп. сервисов | architecture / security / integration-guide / ADR — роль 5 |
| 06 | Метрики пользы и способ проверить эффект | metrics.md + A/B через feature flags + Grafana — роли 1, 5 |

**«Действие выполнено»** по ТЗ = сервис/имитация вернул результат, помощник его **отобразил и сохранил**.

## 3. Жёсткие ограничения (нарушение = потеря баллов или недопуск)
- **Покрытие строк своего кода тестами > 80%** + воспроизводимый отчёт инструмента покрытия.
- **SDD-спецификации** (spec-kit / OpenSpec), по которым велась разработка AI-функций.
- **Права пользователя**: недоступное не раскрывается и не выполняется.
- Только **синтетические данные**; тестовые инструкции **не выдавать за регламенты Авито**; не строить свои HR-системы; без чувствительных ПДн и финансовых операций.
- **UI < 1 с** на локальные операции; LLM/сервисы не блокируют интерфейс, есть статус ожидания и обработка сбоев.
- Стек, совместимый с Авито: Go (Python+Flask в отдельных случаях), PostgreSQL, Redis, React + TS + TanStack + Zustand + Zod. Важна совместимость архитектуры, а не все технологии подряд.

## 4. Что сдаём
1. Работающий прототип со всеми заявленными сценариями.
2. Код + **README.md** (запуск через Docker, версии зависимостей, тестовые учётки, порядок проверки, запуск тестов) + SDD-спецификации + тесты + отчёт о покрытии.
3. Тестовые данные и имитации интеграций.
4. **Видео** «от запроса до результата» (файл или ссылка на 1-м слайде / в README).
5. **Продуктовая презентация PDF** (на платформу — PDF со ссылкой на репозиторий или ZIP). Приватный репозиторий → доступ аккаунту `hack-and-change-2026`.
6. Для внешних API: сервис, модель, переменная окружения, как подключить ключ + пример конфига без секретов.

**Недопуск (0 баллов)**: прототип не запускается по инструкции / эксперт не проходит основной сценарий; нет кода или инструкций; нет презентации. → Поэтому у нас **обязательный режим без LLM-ключа** (`LLM_PROVIDER=mock`), который проходит все сценарии.

Выводы: (1) **интеграционная история** (MCP, авторизация, роли, feature flags, ИИ-крон, Clickstream/Grafana, план подключения к реальным сервисам) весит больше всего — ей выделена отдельная роль; (2) **UX и демо** — вторая опора; (3) лучше **4 отлаженных сценария**, чем 5 сырых — количество не даёт баллов; (4) «командное владение» — каждый должен уметь рассказать про всю систему, не только про свою часть.

## 6. Наши решения (зафиксированы в общем контексте каждого промпта)
- **Сценарии**: S1 «Что делать дальше?» (трекер адаптации по чек-листу Авито), S2 вопросы о команде/инструментах (RAG с правами), S3 оформление отгула (действие), S4 запрос доступов (действие), S5 вопрос наставнику / повестка 1:1 — опционально.
- **Архитектура**: React-фронт → core-api на Go → agent на Python/Flask → corp-mock на Go (REST + MCP). PostgreSQL + Redis. Docker Compose, GitHub Actions, Prometheus/Grafana.
- **Безопасность действий**: агент создаёт только черновик, отправка — после подтверждения стажёром в UI. Права проверяются в трёх местах.
- **Тестовые учётки**: `intern_anna`, `intern_max`, `mentor_igor`, `lead_olga`, `hr_elena` (пароль `buddy2026`, данные синтетические).
- Все контракты API (A — фронт↔core, B — core↔agent, C — MCP-инструменты, D — core↔corp-mock) прописаны в общем контексте: каждый может работать на моках с первой минуты.

## 7. Пять ролей и баланс нагрузки
| Роль | Главное | Код | Документы / прочее | Влияет на критерии |
|---|---|---|---|---|
| **1. Product Lead (продукт, контент, QA)** | CJM, сценарии и критерии приёмки, база знаний и сиды, e2e, метрики, презентация, видео, подготовка к защите | e2e на Playwright | metrics, demo-script, qa-checklist, презентация, видео, Q&A к защите | демо 25%, ценность 20%, презентация, работоспособность |
| **2. Frontend** | весь UI: вход, панель адаптации, чат, карточки действий, история, уведомления, режим наставника | React/TS + Vitest/MSW, покрытие > 80% | спецификация UI, раздел README | UX 25%, демо 25% |
| **3. Backend core-api (Go)** | авторизация и роли (имитация), онбординг и next_steps, оркестрация чата, жизненный цикл действий, ИИ-крон, feature flags, события | Go + тесты > 80%, OpenAPI | спецификации core-*, матрица прав | тех. реализация 15%, обоснованность 20%, работоспособность 20% |
| **4. AI-инженер (agent)** | LLM-оркестрация, tool-calling через MCP, RAG с правами, guardrails, mock-режим без ключа, evals | Python/Flask + pytest > 80% | SDD-спецификации agent-* (обязательны по ТЗ), ai-quality | работоспособность, безопасность, обоснованность |
| **5. Platform & Integrations** | corp-mock (имитации сервисов отсутствий, доступов, справочника) + MCP-сервер, Docker Compose, CI, сводное покрытие, Grafana, архитектура и план внедрения, финальный README и сдача | Go + тесты > 80%, инфраструктура | architecture, security, integration-guide, ADR, README | внедряемость 30% + 25% |

Баланс: у трёх «чисто кодовых» ролей (2, 3, 4) — по одному сервису плюс спецификации и покрытие. У ролей 1 и 5 меньше прикладного кода, но они несут самые весомые нетехнические артефакты (презентация, видео и демо — у 1; архитектура, внедряемость, инфраструктура и сдача — у 5), а роль 5 ещё и пишет свой сервис corp-mock. Роль 1 пишет e2e-тесты, чтобы не быть «только про слайды».

## 8. План по времени (доли от длительности хакатона)
| Этап | Что происходит | Критический путь |
|---|---|---|
| 0–10% | Роль 5 — каркас репозитория и compose со стабами; роль 1 — сценарии и критерии приёмки; роли 2–4 — спецификации и OpenAPI | Каркас репо (5), критерии приёмки (1), OpenAPI (3) |
| 10–60% | Параллельная разработка на моках по контрактам A–D | MCP-сервер corp-mock (5) → агент (4); mock-режим агента (4) |
| 60–80% | Интеграция в Docker Compose, e2e по всем сценариям, добивание покрытия, Grafana | e2e зелёные (1), CI с порогом 80% (5) |
| 80–100% | Feature freeze, полировка UX, запись видео на стабильной сборке, презентация, прогон README «с нуля», репетиция защиты | Видео + презентация (1), README и сдача (5) |

Синхронизации: короткий созвон каждые ~4 часа (что готово / что блокирует / изменения контрактов). Любое изменение контракта — только через общий чат и правку общего контекста.

## 9. Как пользоваться промптами
1. Каждый открывает свой файл в папке `prompts/` и копирует его целиком в новый чат нейросети (лучше с поддержкой длинного контекста и файлов).
2. Прикрепляет PDF с ТЗ (`Авито_кейс.pdf`).
3. Нейросеть начнёт с шага 1 своего «порядка работы». Дальше работаете итерациями.
4. Общий контекст в начале каждого промпта одинаковый — он и есть «договор» команды. Если меняете контракт — обновите его во всех пяти файлах.

Источник чек-листа стажёра Авито (использован для этапов адаптации): публичная таблица из раздела «Источники информации» ТЗ.
